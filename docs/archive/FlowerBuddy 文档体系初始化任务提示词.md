## 给 AI Agent 的完整任务指令

你正在维护我的 Windows 桌宠个人助手项目 **FlowerBuddy**：

- GitHub 仓库：<https://github.com/ZaiHuaOvO/FlowerBuddy>
- 技术栈：Electron、electron-vite、React、TypeScript、Vite、Vitest、electron-builder；具体版本和命令必须以当前仓库的 `package.json`、锁文件和配置为准。
- 项目现有规范文件包括 `README.md`、`Windows_桌宠个人助手_技术开发文档.md`、`DESIGN_SYSTEM.md`、`GIT_WORKFLOW.md`、`PRIVACY.md`，以及 `docs/OPEN_ITEMS.md` 和视觉回归截图。请先核对它们是否仍存在、内容是否与当前实现一致，不要只依赖本提示词里的描述。
- 项目已经完成第一阶段主要功能及一轮架构/性能优化。接下来准备进入功能与样式的详细测试。**本任务只建立常规开发所需的 Agent 规则和文档体系，不要提前执行大规模功能测试、样式重做、业务重构或新功能开发。**

### 一、执行前必须完成的检查

1. 确认仓库根目录、当前分支、远程地址、工作区状态和最近提交。严格遵守 `GIT_WORKFLOW.md`。
2. 如果工作区中有用户未提交的修改，先识别并保留；不要覆盖、丢弃或混入本任务之外的改动。
3. 阅读现有文档：`README.md`、`Windows_桌宠个人助手_技术开发文档.md`、`DESIGN_SYSTEM.md`、`GIT_WORKFLOW.md`、`PRIVACY.md`、`docs/OPEN_ITEMS.md`。
4. 实际检查 `package.json`、`electron.vite.config.ts`、`electron-builder.yml`、TypeScript/ESLint/Vitest/Prettier 配置，以及 `src/`、`tests/`、`scripts/` 的当前结构。根据代码事实建立文档，不能只从旧文档复制架构。
5. 给出现状差异清单：现有文档里哪些内容已准确、哪些过期、哪些缺失、哪些互相冲突。不要先大范围修改，先辨认证据和影响。

### 二、本次任务的目标

建立一套**简洁、可导航、彼此不冲突、长期可维护**的项目规则体系，使后续每个 AI Agent 在开始任务前知道该读什么、改代码时遵守什么，以及何时必须同步文档。

必须完成下列工作：

#### 1. 在仓库根目录创建 `AGENTS.md`

注意文件名是 **`AGENTS.md`（复数）**，不是 `AGENT.md`。这是 Codex 等工具常用的项目指令文件名；如项目还会使用其他 Agent，要说明这些 Agent 是否原生读取该文件，并给出必要的引用/入口配置建议，但不要无依据声称所有工具都会自动加载它。

`AGENTS.md` 是**操作规则入口，不是百科全书**。保持聚焦、清晰，避免复制其他文档的大段内容。至少覆盖：

- 每个任务开始前的必读流程：检查 Git 状态，阅读本文件、`docs/README.md` 文档索引及与当前任务相关的规范。
- 任务分类与文档路由：功能、UI/样式、架构、IPC、安全/隐私、测试、构建/发布、依赖升级、纯文档修改分别需要阅读哪些文件。
- 先调查再修改：先读调用链和现有实现，不凭文件名猜测，不随意创建重复公共组件/工具/服务，不把项目改造成由孤立页面或重复逻辑拼接的结构。
- 代码质量约定：TypeScript 类型边界、主进程/preload/renderer 的职责、IPC 安全、模块职责与依赖方向、公共组件复用、错误处理、日志脱敏、配置迁移、异步任务生命周期等。只写已从源码确认或经维护者认可的规范；不确定的内容标记待核实。
- 设计约束：UI 工作必须阅读 `DESIGN_SYSTEM.md`，使用现有 token 与公共组件，样式修改要考虑视觉回归，不得在组件里随意新增一套硬编码设计值。
- 测试约束：先查看 `package.json` 的真实 scripts；根据改动运行适用的类型检查、lint、测试和构建。必须如实报告未执行或失败的检查。
- 文档同步规则：任何行为、架构、IPC、配置、设计规则、测试策略、隐私行为、依赖、构建或发布流程的真实变化，都必须评估并同步相关文档；代码与文档应在同一任务、同一逻辑提交中完成。
- Git 约束：遵守 `GIT_WORKFLOW.md`；审查 diff、避免提交密钥，完成独立更新后按现有规范提交和推送，推送后验证状态，并用“一句话总结 + 每条详细改动各一句话”的方式汇报。
- 明确禁止：未经授权大范围重构、擅自改变产品行为、伪造测试结果、把计划功能写成已完成、未经同意执行破坏性 Git 操作、将秘密信息写入文档或仓库。
- 结束任务时的报告格式：总结、变更文件、验证证据、未解决事项、提交/推送状态。

#### 2. 创建或完善 `docs/README.md`

把它作为**文档索引与单一入口**。为每份文档说明：

- 负责回答什么问题；
- 哪些任务开始前必须阅读；
- 哪些代码变化会要求同步修改；
- 它是当前事实、操作规范、用户文档，还是历史/初始规划材料。

建立一张“改动类型 → 必读文档 → 需要同步更新的文档”表。至少覆盖功能行为、React UI/样式、窗口或 IPC、业务模块/API、配置和迁移、隐私/安全、测试策略、依赖、构建/打包、Git/Agent 规则。

#### 3. 基于当前源码建立架构文档

优先创建 `docs/architecture/overview.md`，按实际源码说明：

- Electron main、preload、renderer、shared 的职责与边界；
- 当前主要目录与关键入口文件的职责；
- 窗口创建与各 renderer view 的关系；
- IPC 的调用方向、校验、响应类型和安全边界；
- 功能模块注册、启动/停止生命周期、统一调度器的关系；
- 普通配置、敏感凭据、用户导入资源和日志的存储位置与流向；
- 当前实际的构建/打包数据流；
- 关键依赖方向以及禁止出现的反向依赖。

可以增加一张 Mermaid 架构图，但必须根据源码绘制。不能将计划中的架构、尚未实现的设计或推测写成当前事实。

若 IPC 契约较多且已有类型/通道定义不够容易导航，再按实际需要补充 `docs/architecture/ipc-contracts.md`；不要为追求文档数量而拆分。

#### 4. 建立开发约定

创建 `docs/development/coding-guidelines.md`，记录本项目当前实际采用的代码组织、命名、类型、模块、公共组件、错误处理、日志、配置/secret 管理、依赖方向和新增模块的约定。

要求：

- 先从现有源码、Lint/TypeScript 配置和测试风格中提取规则；
- 区分“已存在的约定”和“建议未来采用的改进”；
- 不要为了把规则写进文档而顺手批量改造代码；
- 不要规定机械的最大文件行数作为唯一质量标准，判断是否拆分要以职责、耦合、测试性和实际变更风险为依据。

#### 5. 为即将开始的功能和样式测试准备测试文档

创建：

- `docs/testing/strategy.md`：测试分层、测试范围、如何运行真实 scripts、单元/集成/手动/视觉回归的职责与限制；
- `docs/testing/manual-test-plan.md`：可逐条勾选的功能验收清单和视觉检查清单。

手动测试计划至少按实际功能覆盖：桌宠窗口与拖动/点击、托盘、设置和持久化、模块开关、日期事件、网站可用性检查、DeepSeek、ESA、Gmail OAuth/新邮件/去重、网络错误、失效凭据、休眠恢复、启动与退出、安装/升级/卸载等。

视觉清单至少覆盖：桌宠透明边缘与缩放、菜单、各类气泡状态、所有设置分页、控件默认/hover/pressed/focus/disabled/loading/error/empty 状态、长文本与窗口尺寸、常见 Windows DPI、键盘可用性及减少动态效果。

重要约束：

- 本次只编写测试方法和清单，不要声称测试已经通过，也不要伪造截图或实际账户测试结果。
- 已完成、待测、已知限制、计划支持要分开标记。
- 检查当前 `docs/OPEN_ITEMS.md`，将它作为未完成项的入口并避免重复维护第二份互相冲突的待办清单。
- 如果某项测试需要真实 Gmail、DeepSeek 或阿里云凭据，要写清前置条件；不得将密钥写进测试报告、文档或仓库。

#### 6. 处理当前已有文档的职责与冲突

不要直接删除或大幅重写已有文件。先判断并明确：

- `README.md`：面向使用者与贡献者的项目入口、快速上手和常用命令；
- `Windows_桌宠个人助手_技术开发文档.md`：它仍是当前约束、已完成实现说明，还是原始开发计划/历史材料？根据事实在顶部增加状态说明并修订过期内容，防止 AI 将早期计划误当成当前实现；
- `DESIGN_SYSTEM.md`：UI 规范唯一入口；
- `GIT_WORKFLOW.md`：Git 操作唯一入口；
- `PRIVACY.md`：对用户公开的隐私行为说明；
- `docs/OPEN_ITEMS.md`：未完成项和已知限制入口。

如果两份文档重复表达同一条规则，尽量只保留一处详细说明，其他位置通过链接引用。对无法从代码确认的内容，标注“待核实”，不要擅自决定。

#### 7. 设计“规则和文档同步”机制

在 `AGENTS.md` 与 `docs/README.md` 中写清以下流程：

1. 接任务前：检查 Git 状态，读 `AGENTS.md`、文档索引和相关具体文档。
2. 开发前：确认现有行为、相关调用链、验收条件以及预计影响的文档。
3. 实施时：同时考虑代码、测试与文档，不把文档更新留到不确定的未来。
4. 完成前：逐条检查文档是否与最终代码一致，检查链接和 Markdown 格式。
5. 提交前：代码和文档在同一逻辑变更内；运行适当检查并审阅 diff。
6. 提交后：遵守 `GIT_WORKFLOW.md` 推送并验证远程结果；报告真正完成的事项。

将文档同步要求做成可操作的影响矩阵，而不只写“记得更新文档”这句空泛口号。

### 四、文档准确性与维护原则

1. **源码反映当前行为，文档负责解释和约束。** 当现有文档与代码冲突，先查清目标与证据；不得盲目让代码服从过期文档，也不得默默改变产品行为来消除冲突。
2. **区分事实与提议。** 使用“当前已实现”“待验证”“计划/建议”明确状态。没有真实运行记录，就不得声称测试通过；没有真实测量，就不得声称性能提升了某百分比。
3. **单一权威来源。** 同一规则只在一份文档中详细维护，索引或其他文档使用链接指向它。
4. **文档规模从简。** 优先写明操作流程、边界、职责与验收标准；不大段复制源码，也不将所有实现细节写入 `AGENTS.md`。
5. **每次规则变更同步。** 修改开发规则、架构边界、IPC 行为、设计 token、隐私行为、测试/发布流程或 Git 工作流时，必须同步更新其权威文档和索引/引用。
6. **新增或改变用户可见行为时**，同步评估 README、手动测试计划、已知限制/待办和隐私说明是否需要更新。
7. **不存秘密。** 不要将真实 API Key、AccessKey、OAuth token、邮箱数据、个人配置或日志写入文档、截图、测试夹具或 Git。
8. **避免文档漂移。** 如果无法确认某一条，注明待核实与核实办法；不要猜测后写成事实。
9. **不增加不必要的工具或依赖。** 这次不要为了文档治理引入新的文档生成框架、静态站点、检查器或 npm 依赖，除非已有仓库基础能低成本实现且确实有价值。
10. **本任务不要改业务代码。** 若发现代码缺陷或文档差异，只记入报告/`docs/OPEN_ITEMS.md`，除非是为链接/说明必须进行的最小文档更正。

### 五、验证与交付要求

本任务结束前需要：

1. 核查新建文档链接都指向真实存在的路径；Markdown 标题、代码块和列表格式正确。
2. 运行 `git diff --check`。如果仓库存在 Markdown lint 或文档检查脚本，可运行已存在的脚本；不要只为这次任务新增依赖。
3. 按影响范围运行必要的检查。纯文档变更不必无理由重跑所有业务构建，但必须说明运行了什么、没有运行什么。
4. 检查 `git diff --stat` 和完整 diff，确认没有不相关代码改动、删除截图、生成产物、用户数据或任何秘密。
5. 按 `GIT_WORKFLOW.md` 做提交和推送。开始前先确认远程、分支、工作区与认证状态；不要覆盖其他人的修改，不要 force push。若无法推送，必须如实说明，不得伪报。
6. 最终报告采用以下格式：

```text
一句话总结：完成 FlowerBuddy 常规开发阶段的 Agent 规则与文档体系初始化，并已推送至 GitHub（仅在真实成功时这样写）。

详细改动：
- 新增 AGENTS.md，规定任务前检查、文档阅读、编码/测试、安全和文档同步流程。
- 新增 docs/README.md，整理文档索引、权威来源和改动影响矩阵。
- 新增 docs/architecture/overview.md，按当前源码记录真实架构与数据流。
- 新增/更新开发约定和测试策略/手动验收清单。
- 对旧开发文档标明适用范围，记录已发现的过期信息或待核实项。

验证结果：
- git diff --check：通过/失败（真实结果）。
- 文档链接/格式检查：通过/失败/未执行及原因。
- 单元测试/类型检查/构建：已执行的列出真实结果；未执行的明确说明原因。

未解决事项：逐条列出需要之后处理的内容；无则写“无”。

Git 状态：分支、提交短哈希、远程推送验证状态；不能确认时明确说明。
```
