# 阶段 F：I/O 决策、CI 与最终回归

> 完成日期：2026-10-17
> 对应审计阶段：阶段 F
> 基线：[docs/performance-baseline.md](performance-baseline.md)

## 1. 同步 I/O：测量后决定不改

按审计要求，只有基线显示值得时才改异步。实测当前热缓存下：

| 操作                                   | 平均耗时 |
| -------------------------------------- | -------: |
| `readFileSync` 15 MB                   |  4.37 ms |
| `writeFileSync` 15 MB 复制             |  4.99 ms |
| 单条日志 `appendFileSync` + `statSync` |  0.33 ms |

相对最终约 500 ms 的宠物挂载时间，这些同步操作不构成可测的主进程阻塞；自定义桌宠图片导入也是低频操作。因此本阶段**没有**把配置、JSON 存储、日志或图片导入改成异步队列，避免为没有证据的问题增加复杂度。

如果后续出现大文件、日志集中爆发或用户可感知的卡顿，再根据新的测量单独处理。

## 2. CI 与 Windows 打包任务

新增 `.github/workflows/ci.yml`：

- 触发：推送到 `main`、`v*` 标签、Pull Request、手动 `workflow_dispatch`。
- `check` 任务（`windows-latest`）：`npm ci` → typecheck → lint → format check → 单元测试 → 生产构建。
- `package` 任务（手动触发或 `v*` 标签）：执行 `npm run dist:win`，上传 Setup、Portable、ZIP 和 blockmap 为构建工件。
- 设置 `CSC_IDENTITY_AUTO_DISCOVERY=false`，避免无证书的 CI 环境尝试自动发现签名证书。
- 没有在 CI 中注入任何真实 Gmail、DeepSeek 或阿里云凭据。

该工作流尚未在 GitHub 托管运行器上实际执行；推送后由 GitHub 首次运行验证。本地已按相同顺序执行全部命令。

## 5. 阶段 A–F 最终对比

| 指标                | 基线（阶段 A） |          最终 |      变化 |
| ------------------- | -------------: | ------------: | --------: |
| 宠物内容挂载中位数  |        1182 ms |        499 ms |   约 -58% |
| 启动后工作集        |       523.5 MB |      365.3 MB | -158.2 MB |
| 启动后私有内存      |       346.2 MB |      193.5 MB | -152.7 MB |
| 主进程工作集        |       286.3 MB |     约 138 MB |   约 -52% |
| renderer 入口 JS    |      256,621 B |     227,973 B |    -11.2% |
| renderer 入口 CSS   |       15,850 B |      10,642 B |    -32.9% |
| 主进程 bundle       |    1,492,998 B |     149,481 B |    -90.0% |
| `app.asar`          |  102,273,225 B | 102,285,190 B | +11,965 B |
| NSIS Setup          |  116,827,782 B | 116,826,548 B |  -1,234 B |
| ZIP                 |  116,627,911 B | 116,626,697 B |  -1,214 B |
| 单元测试            |         184 项 |        199 项 |    +15 项 |
| `SettingsApp.tsx`   |       1,735 行 |        440 行 | -1,295 行 |
| `app-controller.ts` |         956 行 |        490 行 |   -466 行 |

结论：

- 启动与内存的主要收益来自 Gmail/ESA SDK 延迟加载，不是代码拆分本身。
- renderer 代码分割与设置页拆分改善了加载边界与可维护性；设置页首次打开会多约 257 ms 的 chunk 加载，这是已记录的取舍。
- 安装包体积基本不变；动态导入与代码分割只影响加载时机，不减少分发体积。
- 未采用会让宠物挂载变慢约 294 ms 的四视图全懒加载方案，也未在无测量证据时改动同步 I/O。
